# T05独立保留约束修复与一条命令自主确认

2026-10-10本地实现，服务器验收待运行。只在本地编辑新代码、文档并进行静态核对；没有运行本地项目Python、测试、模型、训练或环境，也没有上传/修改服务器代码。继续由用户提交、推送、在服务器拉取并运行。

## 为什么换成独立修复

旧400修复提高了保持事实拟合，却让原参考八项NLL超过0.02保留限度。最新冲突诊断确认183/184固定目标状态noop概率增大，184/184下转−noop偏好下降，参考jump和旧下转也受损。见 [已验收诊断分析](t05_within_horizon_conflict_result_analysis.md)。

本轮从生产350重新开始，在事实NLL之外约束冻结350的完整动作分布。目标是减少新保持拟合对旧行为的破坏；350原自主gate本身未通过，分布约束不能保证新自主控制有效。目标1的新预算内训练纠偏依然缺失，不能靠重采样或模型分布补成独立证据。

新生产版本也是350+50=400，但使用独立`ls_imagine_retention_repair_worker_v1`格式、协议、模型内容ID和输出目录。旧`within_horizon_repair`的400及其FAIL/WARN保持，不接受旧400、best、验收副本或中途checkpoint作为新生产模型。51个旧验收代码不修改。

## 固定协议与成本

- 两分支分别继承生产350权重，新Adam步0；训练种子7，学习率`1e-5`，各固定50次更新，批256。固定最终latest，阶段指标只报告，不用于选best、延预算或自动调参。
- 每批事实NLL仍为192原训练、48原参考训练（两目标各24）、16全部新手工训练池均匀有放回。新手工池全部24事实，23noop/1上转；开发16、worker40、旧84帧40都不加入该NLL。
- 教师为已独立verify的冻结生产350，完整12动作概率作为分布保留参考，含原一次unimix。教师无优化器、不接受梯度，参数内容、版本和缓存全程核对，不能当专家标签。
- 原训练KL使用本批相同192原训练状态及自身目标，权重1；参考KL使用全部32参考训练状态，各有自身终点和原固定目标两个上下文，权重4；旧84帧KL使用全部12手工训练状态，同样两个上下文，权重4。参考validation、开发及worker事实不得进入锚点，不挑唯一下转过采样。
- 参考保持自身frame64–79/remaining16–1/80帧终点；旧续段保持自身frame80–83/remaining4–1/84帧终点，不移植到新76–79状态。每头缓存64参考+24旧续段=88上下文。新24事实继续绑定本局真实第80帧事后目标；部署只用原两个固定视觉目标。
- 固定训练100次双头优化器更新、每头12800事实采样标签、环境步0。生产训练教师查询为176次缓存初始化+19200次原训练前向=19376；参考/旧续段每头缓存使用3200/1200次，重复使用不算独立证据。check查询176；verify两个内存副本各初始化176及一次额外混合更新384，共1120教师查询，额外四次优化器更新不保存到生产latest。
- 原26局与两目标/自身及固定目标/两头的10项保留检查仍为NLL绝对增加≤0.02。失败原样保存。事实NLL、KL、实际/固定目标结果、保持/上转/下转、旧84帧和原参考分别报告。

每头训练目标为：原三池事实NLL + 原训练KL + 4×参考训练KL + 4×旧手工训练KL。其中KL为`KL(冻结350 || 当前部署概率)`，按各池行均值计算。权重和学习率在新check中锁定，不根据开发结果调整。

## 服务器只运行这一条

先把本地改动通过Git提交、推送，再在服务器项目中拉取。不要手工拷贝这些文件到服务器，也不要重跑旧修复或成功冲突诊断。在`(ls)`环境、项目根目录执行：

```bash
MINEDOJO_HEADLESS=1 python scripts/t05_retention_pipeline.py \
  --diagnosis-dir "$PWD/relevance_map/t05_outputs/within_horizon_conflict_diagnose_20261010T043105_981616" \
  --device cuda:0
```

自动创建独立`relevance_map/t05_outputs/retention_pipeline_<时间戳>/`，依次运行：

1. `repair_check`：严格历史SHA、原350重现、教师/锚点/分布/梯度/负守卫及预声明计划，更新0。
2. `repair_train`：固定50步双分支修复，独立latest及各池计数。
3. `repair_verify`：严格恢复、独立无优化器推理、教师绑定及计数、两内存副本下一混合更新等价，生产预算不变。
4. 只有全部10项保留通过，才运行`confirmation_check`，核对生产模型、因果执行接口、计划和原门槛，环境步0。
5. `confirmation_evaluate`：两目标×goal/no_goal/swapped_goal×5次独立fresh reset；新顺序种子7、固定mode、原32noop+32前缀+16控制，最多2400真实环境步，无手工干预、补样或重试。

每个阶段是独立进程，结束后释放模型内存。总流程不能resume；已有输出目录拒绝覆盖。任一步异常就停止后续阶段，并保留报告、错误和日志；保留未通过就不启动环境。真实早停或缺测保留，不能用最佳中间帧替换第16步终点。

## 结果如何判读和接收

根目录`report.json`是总报告；`retention.json`和`gate.json`分别保存两个门槛，阶段目录保留完整报告和原始产物。末尾输出`PIPELINE RESULT`：

| 总状态 | 含义 | 返回码 |
| --- | --- | ---: |
| `failed` | 某阶段工程失败，后续停止 | 2 |
| `retention_not_passed` | 修复/verify工程通过，10项保留有超限，不执行自主确认 | 3 |
| `behavior_not_passed` | 保留通过，自主确认工程通过，原逐目标行为门槛未达 | 3 |
| `human_review_required` | 保留和数值行为门槛通过，等待完整视频及物理一致性人工核对 | 0 |

行为门槛不变：每目标goal至少4/5次同时正进展和正确终点偏好；每目标五次goal平均进展为正，并胜no_goal和交换组。必须全部30次工程有效。人工核对通过之后，才可按 [原T06准入规则](t05_to_t06_gate.md)推进当前场景的小规模采集；本工具始终`human_review_pending=true`、`t06_approved=false`，不把工程PASS或loss下降当准入。

最后统一打包总报告、已产生的五阶段报告/表格/图片及成功冲突诊断。使用原汇总器的字节/SHA/64MiB限制，不截断结果；大模型、轨迹数组和视频留在服务器。完整视频仍需后续人工查看，结果包不能替代视频验收。无需每阶段重复打包、逐个下载或重命名。末尾仅反馈`FEEDBACK_INDEX`或`OUTPUT_DIR`，助手按现有授权通过T2-3090只读接收结果到电脑。见 [接收说明](t05_result_bundle.md)。
